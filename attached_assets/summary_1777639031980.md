# Project Summary — Bug Bounty Pro (frontend + backend)

This document provides a comprehensive overview of the repository, architecture, frontend, backend, data model, services, development and runtime workflows, tests, known issues, and notes to reproduce or extend the project. It aims to capture every important detail needed to understand, run, and modify the application.

---

## 1. High-level overview

- Purpose: a web-based vulnerability assessment / bug-bounty oriented scanning platform with a React frontend and Python backend. The system schedules and runs automated scan jobs, aggregates findings, exposes an operator UI, and supports programmatic public API endpoints and remediation workflows.
- Main stacks:
  - Frontend: React + TypeScript, Vite, Wouter routing, CSS (global stylesheet with CSS variables).
  - Backend: Python (FastAPI), SQL-alchemy style DB access (session), modular routers under `app/api/routes/`, service layer in `app/services/`.
  - Workers: background worker queue (`workers/`), scanning orchestration in `app/services/scanner_execution.py` and `app/services/scanner_catalog.py`.

---

## 2. Repository layout (top-level)

- `app/` — backend application code (FastAPI):
  - `main.py` — application entry, startup/shutdown hooks, rate limiting and CORS, mounts React `web/dist` for SPA serving, includes API routers.
  - `api/routes/` — API routes split by concern (e.g. `auth.py`, `public_api.py`, `remediations.py`, `scans.py`, `settings.py`, ...).
  - `core/` — core utilities like `auth.py`, `config.py`, `rbac.py`.
  - `db/` — `session.py` database session and initialization helpers.
  - `models/` — ORM models such as `scan.py` (scan job models / DB entities).
  - `schemas/` — Pydantic schemas for API request/response (`auth.py`, `scan.py`, `metrics.py`, ...).
  - `services/` — large collection of service modules (scanner orchestration, reporting, notifications, recon, fuzzing, AI report synthesis, monitor, live_events, rate_limiter, etc.).
  - `workers/` — `queue.py` and `worker.py` for background job processing.

- `web/` — frontend (React + TypeScript + Vite):
  - `package.json`, `vite.config.ts`, `tsconfig.json` and `src/`.
  - `web/src/` contains source code; notable files edited in current project: `index.css`, `App.tsx`, `components/Shell.tsx`, `pages/*` (CommandCenter, ScansList, ScanNew, FindingsList, TargetsList, SystemStatus), `lib/useApi.ts`, `lib/explorer.ts`.

- `tests/` — Python tests: unit and integration tests, with `e2e/` and `integration/` subfolders (these validate backend logic and flows).
- `scripts/` — helper scripts like `e2e_test.py`, `generate_dev_token.py`.
- Top-level support files: `run_pipeline.py`, `requirements.txt`, `README.md`, `EXECUTION_PLAN.md`, `SECURITY.md`, design docs and plans.

## 3. Frontend details

### 3.1 Technologies & build

- React (TypeScript)
- Vite for dev/prod build and preview (`npm run dev`, `npm run build`, `npm run preview`).
- Wouter used for client-side routing in `App.tsx`.
- Styling: single global stylesheet `web/src/index.css` that defines design tokens (CSS variables) and component primitives (cards, pills, chips, data-tables, profile buttons, form sections, toggles).

### 3.2 Entry points and routing

- `web/src/main.tsx` (typical) bootstraps React into `#root` and renders `App`.
- `web/src/App.tsx` defines routes:
  - `/` — `CommandCenter` (dashboard/operations console)
  - `/scans` — `ScansList` (list and table of scan jobs)
  - `/scans/new` — `ScanNew` (new scan form)
  - `/scans/:id` — single scan console (`ScanConsole` / `ScanView`)
  - `/findings` — `FindingsList`
  - `/findings/:id` — single finding view
  - `/targets` — `TargetsList`
  - `/system` — `SystemStatus`

### 3.3 Layout and shared components

- `components/Shell.tsx`: App shell component providing the sidebar, topbar, and main content area. Responsibilities:
  - Primary navigation (Dashboard, Scans, Findings, Targets, System, New Scan index link)
  - Branding and compact/expanded sidebar behavior via CSS media queries
  - Topbar elements like search, notifications icon, auth status (auth/login hooks)
- `web/src/index.css` contains tokens and style rules for:
  - Colors: `--bg`, `--surface-0`, `--surface-1`, `--line`, `--accent`, `--muted`, `--text`, status colors (`--crit`, `--high`, `--med`, `--low`, `--info`).
  - Component primitives: `.card`, `.kpi-grid`, `.pill`, `.chip`, `.data-table`, `.form-section`, `.profile-btn`, `.toggle-row`.
  - Responsive layout: sidebar expands on screens >=981px to 256px, collapses to minimal icons on smaller screens.

### 3.4 Data & API integration (client-side)

- `web/src/lib/useApi.ts`: collection of React hooks that encapsulate HTTP calls to backend endpoints. Notable hooks:
  - `useScans()` — fetches list of scan jobs
  - `useScan(id)` — fetches a specific scan job details
  - `useScanReport(id)` — fetches full scan report/results
  - `useHealthStatus()` — queries `/health` and other operational endpoints
  - `submitScan(payload)` — posts new scan job to backend and returns created job id
- `web/src/lib/explorer.ts`: client-side helper hooks to aggregate and transform findings & targets into UI-friendly structures (e.g., `useFindingsExplorer`, `useTargetInventory`). These normalize report payloads into inventory cards and filters.

### 3.5 Pages & behavior (brief)

- `CommandCenter` (Dashboard)
  - Renders KPI grid (active scans, findings counts, critical/high totals), throughput bars, donut visual for severities, activity feed, and an active scans table.
- `ScansList`
  - Search/filter UI, table of scan jobs with status pills (queued, running, completed, failed), ability to go to new scan form.
- `ScanNew`
  - Multi-section form: Target, Scan profile (QUICK/STANDARD/DEEP), Engine toggles (validate, fuzzing, bug-bounty-mode), Authorization reference and authorization checkbox, `LAUNCH SCAN` button that calls `submitScan`.
- `FindingsList` & `TargetsList`
  - Exploratory UIs showing findings inventory, filters by severity + validation, card views, target stats and last-scan metadata.
- `SystemStatus`
  - Health KPIs and queue snapshot from `useHealthStatus()` and /scan-jobs endpoints.

### 3.6 Build & dev

- To run frontend dev server:
  - cd `web`
  - `npm install` (first time)
  - `npm run dev` — starts Vite dev server (default localhost:5173; alternate port if 5173 taken). The server used in this workspace started on 5174 during the last run.
- To build for production: `npm run build` – produces `web/dist/` which the backend serves as a static SPA.

## 4. Backend details

### 4.1 Technologies & entry

- Python backend built with FastAPI (ASGI). `app/main.py` is the entry point, it:
  - Initializes DB (`init_db()`), optionally seeds demo data (`seed_demo_data()`)
  - Adds simple in-memory `RateLimitMiddleware`
  - Adds `CORSMiddleware` for local origins
  - Includes routers: `/auth`, `/scan-jobs`, `/api` (remediations), public API, settings, and streaming events router `/events` (SSE via `stream_events`).
  - Mounts static SPA output from `web/dist` using a custom `SPAStaticFiles` to support deep-link fallback.

### 4.2 API routes & responsibilities

- `app/api/routes/auth.py` — authentication endpoints, token management, and developer/github login helpers.
- `app/api/routes/scans.py` (mounted at `/scan-jobs`) — create, list, retrieve scan jobs, status updates, job console endpoints.
- `app/api/routes/public_api.py` — read-only endpoints that expose scan results to public integrations or read-only consumers.
- `app/api/routes/remediations.py` — endpoints for remediation workflows, link findings to issues or tickets.
- `app/api/routes/settings.py` — application and operational settings endpoints.

### 4.3 Services & worker architecture

- `app/services/` contains many modules that implement scanning engines, recon, fuzzing, triage, AI report composition, notifications, monitoring, and other business logic.
- `workers/queue.py` and `workers/worker.py` implement the job queue and worker process that consumes scan jobs. Workers coordinate with `app/services/scanner_execution.py` and `scanner_catalog.py` to schedule, run, and report scans.

### 4.4 Data model

- ORM models in `app/models` represent:
  - scan jobs (scheduling metadata, target, profile, status, progress, results pointer)
  - findings metadata (severity, validation status, evidence)
  - targets inventory
  - user/session/auth artifacts
- `app/schemas/` contains Pydantic models used for validation of requests and responses. These correspond closely to DB models and define the API contract consumed by the frontend hooks.

### 4.5 Persistence and initialization

- `app/db/session.py` provides DB session management and `init_db()` which creates tables. The backend seeds demo data on startup if available (`seed_demo_data()`). The DB backend (sqlite/postgres) and connection string are controlled via `app/core/config.py` and `settings`.

### 4.6 Running backend

- Create Python virtualenv and install requirements:
  - `python -m venv .venv`
  - `.\\.venv\\Scripts\\Activate.ps1` (Windows PowerShell) or `source .venv/bin/activate`
  - `pip install -r requirements.txt`
- Run the app (development):
  - `uvicorn app.main:app --reload --port 8000`
  - Or use provided helper scripts if present.
- On startup the app seeds demo data, starts monitors and mounts the `web/dist` static build if available.

## 6. Observed runtime behaviors & known issues (from current workspace work)

- During development, a corrupted `web/src/index.css` earlier caused a PostCSS parse error during `npm run build` (unknown token / unclosed block). The file was repaired and rebuilt successfully.
- Dev server commonly runs on port `5173` but will auto-increment if the port is busy (observed `5174`).
- Some UI pages depend on backend endpoints; when the backend is not running or returns 500, the frontend shows `Loading...` placeholders or errors in the browser console. For final visual parity ensure the backend is running (or mock API responses) so pages render complete data.
- Simple in-memory `RateLimitMiddleware` is used for protection — suitable for dev/demo but not production-grade.

## 7. How the frontend and backend communicate

- REST API endpoints under the backend routers (notably `/scan-jobs`, `/auth`, `/api` remediations, and public API endpoints) provide data required by frontend hooks in `web/src/lib/useApi.ts`.
- The frontend uses fetch/XHR to call these endpoints. For live events/streaming updates the backend exposes an SSE endpoint at `/events` which the frontend may subscribe to for activity feed and live console updates.

## 8. Developer notes & extension points

- To add a new page: create React component under `web/src/pages`, add route in `web/src/App.tsx`, and add nav item in `components/Shell.tsx`.
- To extend API: add router module under `app/api/routes/`, define Pydantic schemas under `app/schemas/`, add service logic to `app/services/`, and register router in `app/main.py`.
- To add background scanning engines: add a new entry to `app/services/scanner_catalog.py` (engine metadata) and implement execution logic in `scanner_execution.py` + worker integration.
